Scoop as a local dev environment as code

Setting up a Windows machine for development usually means an afternoon of download pages, installers and PATH edits, and a tool you only notice is missing days later. Keeping the tools current is worse, because some of them release several times a month and each update means another installer. Scoop, a command-line installer for Windows, turns the setup into one script in a repository and updates every tool with one command. Anyone can run the script without administrator rights, and it installs the same specified set of tools every time.

How Scoop installs a program

Scoop reads manifests from Git repositories called buckets. The main bucket has command-line tools, extras has GUI applications, and java has JDKs.

Scoop does not repackage programs. A manifest points to the program’s original download and records its hash. Scoop downloads the file, checks the hash, and unpacks it or runs the vendor’s installer with options for a local install.

Everything goes into ~\scoop, inside the user profile, so no step needs administrator rights. This is what makes Scoop usable on corporate laptops, where policy blocks installers that write to Program Files or change the machine-wide PATH. Only global installs with --global and some apps in the nonportable bucket need elevation.

The setup script

# setup-dev.ps1
if (-not (Get-Command scoop -ErrorAction SilentlyContinue)) {
    Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
    Invoke-RestMethod -Uri https://get.scoop.sh | Invoke-Expression
}

scoop install git
scoop bucket add extras
scoop bucket add java

scoop install temurin17-jdk temurin21-jdk maven gradle
scoop install nodejs python go
scoop install gh jq kubectl
scoop install vscode dbeaver

scoop reset temurin21-jdk

The script replaces the setup guide. It goes through code review, a new tool is a one-line pull request, and git blame shows why each tool is there. Running it twice does no harm, because Scoop skips apps that are already installed. A setup guide in prose goes out of date because nobody runs it. A script runs on every new machine, so people see its errors and fix them.

Updates and pinned versions

scoop status lists outdated apps, scoop update --all updates them, and scoop cleanup --all removes old copies. scoop hold keeps one tool at its current version while the others update. Each version is then a decision in the script, not the result of when someone last visited a download page.

Several JDKs

The java bucket has Temurin, OpenJDK and other distributions, such as temurin8-jdk, temurin17-jdk and temurin21-jdk. They install side by side, and one command selects the active one:

scoop reset temurin17-jdk   # legacy project
scoop reset temurin21-jdk   # new project

Nobody edits JAVA_HOME or the PATH by hand. The same command works for Python and other tools with several versions.

Export and import

scoop export > scoopfile.json lists the buckets and installed apps of an existing machine, and scoop import scoopfile.json installs them on another one. This is a quick way to capture a working machine before trimming it into a script.

The export is not a lock file. The import installs the version that each bucket offers today, and it uses the recorded versions only for apps without a bucket manifest. To pin a version, install it explicitly, as in scoop install gh@2.7.0, or hold it.

Private buckets

A bucket is a Git repository of JSON manifests, so a team can run its own. A private bucket holds tools that no public bucket has, such as an internal command-line client or a code generator. It can also point manifests to an internal repository that the company approves.

Beyond developer machines

A Windows build agent that starts fresh for each run can use the same script, so the pipeline and the developers have the same tools. An AI agent can read the script to learn which tools are available.

Compared with other approaches

ApproachStrengthWeakness
Step-by-step guideNeeds no toolNobody runs it, so it goes out of date

Chocolatey and wingetLarge catalogsMany packages need administrator rights and change Program Files, the registry or the global PATH

Containers and Scoop work well together. A container describes the runtime, and the host still needs a JDK, an editor and Git, which Scoop installs.

Limits

  • Scoop runs only on Windows.
  • It does not isolate tools, so tools with conflicting libraries can collide.
  • It installs the latest version unless the script pins one.
  • Volunteers maintain the manifests, so new releases can appear late.
  • Software that needs a system service, a driver or an elevated installer fits poorly.
  • It downloads from each program’s original site. If the company blocks that site, Scoop cannot install the program, and it is no way around company rules.

Scoop does not make builds reproducible. It installs a specified set of development tools on a new machine in about ten minutes and keeps those tools current. The rest of the machine, such as the operating system, its settings and your files, is outside its scope.
