TomEE as code

2026-10-20

TomEE is often still installed by hand or run through an IDE plugin, so each developer, the pipeline and production run a slightly different server. TomEE as code puts the server’s description in the repository, and the Maven build creates the server from it. Every machine runs the same server, from the IDE or the terminal, and nobody follows a setup guide.

This post explains the idea. The second part builds the server with the TomEE Maven plugin and runs it from the IDE or the terminal, and the third part in a container and a cluster.

Servers that drift apart

Over the life of a project, one application ends up with several TomEE servers:

  • each developer unzipped one and set it up in their own way,
  • the IDE starts another one, through a plugin or a built-in server integration,
  • the pipeline may keep one for tests,
  • the production image downloads and patches its own copy.

The IDE server has problems of its own. IDE integrations have bugs and limits, impose conventions foreign to the application’s structure, or need manual setup on each machine. The IDE and the command line then start servers configured in different places.

These servers differ from the start, and small changes push them further apart. A developer adds a JDBC driver to the local lib/. A Dockerfile that asks for latest gets a newer TomEE. Someone changes a setting on the test server and never changes it back. No reviewer sees these changes, and after a while nobody can say which server is correct.

Describe the server and let the build create it

Infrastructure as code solved this for machines and networks. A versioned description states what the infrastructure should be, and a tool builds it from that description.

The Maven project already describes how to build the WAR. It can also describe how to build the server that runs it:

  • the TomEE version and flavour,
  • the libraries to add or remove,
  • the few configuration files that differ from the standard distribution.

Values that change per environment, such as the database URL or a password, stay outside the description. The configuration files refer to them, and each environment supplies them.

The build downloads the declared TomEE, copies the project’s files over it, deploys the application and starts it. The server is a build output, like the WAR, and you can delete it at any time.

What “as code” means in this series

A server counts as code only if it passes these checks.

PrincipleWhat it meansHow to check it
DeclarativeThe repository says what the server is, not the steps to set it upThere is no setup guide beyond one build command
Versioned and reviewableEvery change to the server is a diff that someone can reviewA clean git status means the server is exactly what the repository says
ReproducibleA fresh checkout builds the same serverDelete the build output, build again, get the same result
No manual stateNobody adjusts the server after it is builtYou can delete the server at any time without losing anything
Single sourceEach setting lives in exactly one placeSearch for a value and you find it once
Same server everywhereThe IDE, the container and the cluster run the same descriptionThere is no second server definition anywhere

Problems that go away

Problem with a hand-installed serverWith TomEE as code
A test passes for one developer and fails for another, because of a JAR someone added to their server years agoEveryone who checks out the same commit gets the same server
A new developer follows a setup guide that went out of dateA new developer clones the repository, fills in a few local values and runs one command
The application works when the IDE starts it and fails from the command line, or the reverseThe IDE runs the same Maven command as the terminal, without a server plugin
A test run inherits an old deployment, leftover files or a changed log level from the previous runThe build creates the server again for each run
Several projects share one server, and one project’s library changes another’s behaviourEach project builds its own server in its own build folder
Nobody upgrades TomEE, because nobody knows what was changed in the serverAn upgrade is a diff that the team reviews, tests and can revert with one commit

Limits and costs

  • The server is only as reproducible as the TomEE Maven plugin across versions.
  • You own every configuration file you override, and you must merge TomEE’s changes to it on each upgrade.
  • The configuration of each environment stays out of the server description. It needs its own versioned home, the cluster’s manifests, or the drift moves there.
  • One direct edit to a running server brings back manual state. The principles hold only while every change goes through the repository.

For one developer with one application that rarely changes, a hand-installed server may be enough. For a team, several environments or an application that will run for years, writing the description once costs less than rediscovering the server’s configuration every time something breaks.
