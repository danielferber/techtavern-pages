TomEE as code: the server in the repository

The TomEE Maven plugin builds the server from the repository. The POM picks the distribution and the libraries, an overlay folder holds the changed configuration files, and environment variables supply URLs and passwords. The plugin also strips the applications that TomEE ships for demonstration and administration, so the server runs only your application. One Maven command then starts the same clean server on any developer’s machine, from the IDE or the terminal.

This is the second of three parts. The first part explains why the server belongs in the repository, and the third part runs the same server in a container and a cluster. The examples use a generic application called app with a PostgreSQL database.

The server in the POM

The TomEE Maven plugin downloads a given TomEE distribution, adds and removes libraries, copies your files over it and deploys your WAR.

By default, it also removes content that should not reach production:

  • every application that the distribution ships in webapps/, such as ROOT, docs, manager and host-manager (removeDefaultWebapps),
  • the tomee webapp (removeTomeeWebapp),
  • OpenEJB’s internal application, which the plugin does not deploy (deployOpenEjbApplication).

The server then exposes only your application. Hardening still needs your own settings in the overlay, such as the error pages and the connectors in server.xml.

<properties>
    <tomee.version>10.0.0</tomee.version>
    <postgresql.version>42.7.4</postgresql.version>
</properties>

<build>
    <plugins>
        <plugin>
            <groupId>org.apache.tomee.maven</groupId>
            <artifactId>tomee-maven-plugin</artifactId>
            <version>${tomee.version}</version>
            <configuration>
                <tomeeVersion>${tomee.version}</tomeeVersion>
                <tomeeClassifier>webprofile</tomeeClassifier>
                <context>ROOT</context>
                <libs>
                    <!-- The server manages the connection pool, so the driver belongs to the server -->
                    <lib>org.postgresql:postgresql:${postgresql.version}</lib>
                    <!-- The application brings its own JPA provider -->
                    <lib>remove:openjpa-</lib>
                </libs>
                <systemVariables>
                    <!-- Lets server.xml read environment variables -->
                    <org.apache.tomcat.util.digester.PROPERTY_SOURCE>org.apache.tomcat.util.digester.EnvironmentPropertySource</org.apache.tomcat.util.digester.PROPERTY_SOURCE>
                </systemVariables>
            </configuration>
        </plugin>
    </plugins>
</build>

This block holds every difference between this server and a standard TomEE. An upgrade is a one-line change to a property. context renames the deployed WAR, so ROOT serves the application at / instead of /app.

  • Pin the version. A version such as “latest” changes without a commit.
  • Take library versions from properties. When the WAR compiles against a library the server provides, such as a logging API, both declarations use the same property.
  • Check removals after each upgrade. remove:openjpa- deletes every JAR whose name starts with openjpa-. If a later TomEE renames that JAR, the removal stops matching without any error, so look at the server’s lib/ folder.

mvn package tomee:build assembles the server in target/apache-tomee without starting it, so you can inspect it after an upgrade.

The overlay folder

The plugin copies src/main/tomee/ over the downloaded distribution. A file in src/main/tomee/conf/ goes to the server’s conf/, and the same applies to lib/ and bin/. This folder is the overlay, the only place where you edit server files by hand.

src/main/tomee/
├── conf/
│   ├── logback.xml
│   ├── logging.properties
│   ├── server.xml
│   └── tomee.xml
└── lib/
    └── app/
        └── app.properties

The overlay holds two kinds of files:

  • TomEE files with custom settings, such as server.xml, which replace the originals,
  • new files that TomEE does not have, such as lib/app/app.properties.

Version only the TomEE files you change, and start each one from the same TomEE version. On every upgrade, merge TomEE’s changes to those files into the overlay.

Every server the build creates gets the same overlay files. A setting that changes per environment goes in an environment variable, as the next section shows.

The application’s logger

The application’s logger can read its configuration file from the overlay instead of from the WAR. Each environment can then replace that file without a new build of the application. Put the file in src/main/tomee/conf/ and point the logger to it with a system property:

<systemVariables>
    <!-- ... -->
    <logback.configurationFile>${project.build.directory}/apache-tomee/conf/logback.xml</logback.configurationFile>
</systemVariables>

Maven fills in ${project.build.directory}, so the value is an absolute path on each machine. Each logger has its own property:

LoggerSystem property
Logbacklogback.configurationFile
Log4j 2log4j2.configurationFile
Log4j 1.x and reload4jlog4j.configuration, as a URL such as file:/app/conf/log4j.xml

The container’s entrypoint sets the same property, with the path /app/conf/logback.xml, as the third part shows.

Values from the environment

The database URL, the user, the password and the data directory are examples of values that come from environment variables. The overlay files refer to them with ${...} placeholders, so passwords stay out of the repository. TomEE resolves these placeholders in tomee.xml:

<tomee>
    <Resource id="jdbc/appDS" type="javax.sql.DataSource">
        JdbcDriver = org.postgresql.Driver
        JdbcUrl = ${APP_DB_URL}
        UserName = ${APP_DB_USER}
        Password = ${APP_DB_PASSWORD}
        JtaManaged = true
    </Resource>
</tomee>

Tomcat resolves placeholders in server.xml too, but by default it reads only Java system properties. The system property org.apache.tomcat.util.digester.PROPERTY_SOURCE makes it read environment variables. The POM in the first section declares it in the plugin’s systemVariables. The plugin passes it to the JVM as a -D option when it starts the server. The container’s entrypoint sets the same property, as the third part shows.

One variable for all data paths

An application that reads and writes files needs several paths, such as an input folder and an output folder. If each path is an environment variable, every environment repeats the whole list, in Windows format on the developer’s machine and in Linux format in the container. Use one variable for the root folder and keep the paths below it in the overlay:

# lib/app/app.properties
data.root=${APP_DATA_ROOT}
data.input=${data.root}/input
data.output=${data.root}/output

Each environment then sets only APP_DATA_ROOT, as C:/dev/data on the developer’s machine and /app/data in the container. Java accepts forward slashes on Windows, so the paths below the root work in both. TomEE does not read this file. The application loads it and must resolve the ${...} placeholders itself.

Values on the developer’s machine

Unfortunately, the plugin cannot set environment variables. It has no parameter for them and does not read .env files. The server inherits the environment of the Maven process, so the variables must exist before Maven starts. You can:

  • define them on the machine, as user environment variables,
  • load them with a script before mvn runs,
  • define them in the IDE’s run configuration.

Keep the values in one file outside Git, so every developer fills in the same list:

# local.env (not versioned)
APP_DB_URL=jdbc:postgresql://localhost:5432/app
APP_DB_USER=app
APP_DB_PASSWORD=change-me
APP_DATA_ROOT=C:/dev/data

For the script option, this PowerShell line loads the file into the current session:

Get-Content local.env | Where-Object { $_ -match '^[^#].*=' } | ForEach-Object { $k, $v = $_ -split '=', 2; Set-Item "env:$k" $v }

A new developer creates only this file, from a local.env.example in the repository that lists the variable names without secrets.

One command for the IDE and the terminal

mvn package tomee:run

Maven runs the two steps in order. package builds the WAR, and tomee:run assembles the server in target/apache-tomee, deploys the WAR and starts the server. tomee:run alone would deploy the WAR left by an earlier build, or find none to deploy.

The plugin unzips TomEE over the server left by the previous run and overwrites its files, but files that are no longer in the overlay, old deployments and logs stay. Add clean after you remove a file from the overlay or change the TomEE version:

mvn clean package tomee:run

tomee:run keeps the server in the foreground until you press Ctrl+C. To keep the terminal free, start the server in the background and stop it later:

mvn package tomee:start
mvn tomee:stop

In the IDE, a Maven run configuration runs the same commands, and the IDE’s stop button ends tomee:run. The project needs no IDE server plugin. When someone upgrades TomEE or edits server.xml, the next run on every machine includes the change.

Debugging the server

mvn package tomee:debug

tomee:debug does the same as tomee:run and opens a debug port, 5005 by default. The plugin starts the JVM with suspend=y, so the server waits until a debugger connects. The console shows Listening for transport dt_socket at address: 5005 while it waits. To use another port, add -Dtomee-plugin.debugPort=8000.

The IDE then attaches to that port as a remote debugger:

IDEDebug configuration
IntelliJ IDEARemote JVM Debug, host localhost, port 5005
EclipseRemote Java Application, Standard (Socket Attach), host localhost, port 5005
VS CodeA launch.json entry with "type": "java", "request": "attach", "hostName": "localhost", "port": 5005
NetBeansDebug > Attach Debugger, Socket Attach, host localhost, port 5005

Because the server waits for the debugger, breakpoints in startup code, such as a @Startup bean, also stop. Disconnecting the debugger leaves the server running, and Ctrl+C in the terminal stops it.

Other plugin options

The plugin reference lists every parameter. These help most during development:

ParameterWhat it does
synchronization, reloadOnUpdateCopy changed classes and resources into the running server and redeploy the application without a restart
systemVariablesPass Java system properties to the server’s JVM
argsPass command-line arguments to the JVM, such as system properties, Java agents and memory settings
tomeeHttpsPort, tomeeAjpPortSet the HTTPS and AJP ports, when the application needs them
javaagentsAdd Java agents by Maven coordinates
simpleLogPrint each log entry on one line
checkStartedMake tomee:start wait until the server answers, before integration tests

systemVariables and args apply only when the plugin starts the server. The server that tomee:build assembles for the container does not keep them.

Principles checked

PrincipleHow this setup passes the check
DeclarativeThe POM and the overlay describe the server, and the only instruction is mvn clean package tomee:run
Versioned and reviewableEvery change is a diff, and no local edit hides from git status
ReproducibleDeleting target/ and running again gives the same server
No manual stateclean deletes the server, and the build creates it again from the description
Single sourceThe overlay holds the structure, the environment holds the values, and properties hold the versions

The sixth principle, the same server everywhere, needs a container. The third part builds one from the same description.
